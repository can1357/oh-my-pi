# Закрытие открытых проблем после review fixes: дизайн

Дата: 2026-11-09. База: `origin/main` `81679cade8`.

Источник: журналы SDD трёх планов 2026-11-08 (`.superpowers/sdd/2026-11-08-*/progress.md`),
финальные ревью, живые прогоны и полный прогон тестов на Windows. Документ фиксирует решения;
планы в `docs/plans/2026-11-09-*.md` реализуют их. Пути ниже относительно
`packages/coding-agent/`, если не указано иное.

Решение владельца продукта: в план входят все три группы (хвосты планов, тестовая
инфраструктура, исторические падения Windows); простаивающие субагенты адресуемы через A2A.

## Группа A. Хвосты планов

### A2A

- **A2A-1. Карточка показывает простаивающих субагентов.** Сейчас `src/a2a/server.ts` (~542)
  публикует только Main и субагентов в статусе `running`. Новое правило: Main, затем `running`,
  затем `idle` и затем `parked` (если lifecycle умеет поднять его при доставке), внутри групп -
  по последней активности. Завершённые одноразовые и `aborted` не публикуются. Кап
  `a2a.maxPeerSkills` применяется после сортировки. Доставка к `idle` будит ход, к `parked` -
  поднимает агента существующим путём revive; если подъём невозможен, доставка отказывает так же,
  как сейчас для неизвестного агента. Обновить `docs/a2a.md`.
- **A2A-2. Неоднозначный отправитель.** `findPeer` (`src/a2a/reply-relay.ts`) ищет по skill id;
  при двух мостах с одним `a2a.name` выбор случаен. Правило: если в запросе есть `fromUrl` -
  берётся мост с этим URL; иначе единственный кандидат; при нескольких - автоответ не
  отправляется, запрос остаётся открытым для ручного ответа, в лог пишется список кандидатов.
- **A2A-3. Запись входящего запроса до доставки.** Сейчас запись в реестр входящих
  (`rpc.ts` ~754-761) идёт после доставки по шине, и ход может закончиться раньше записи.
  Записывать до `bus.send`; при отказе доставки - удалять запись.
- **A2A-4. Гонка регистрации.** Если ref зарегистрирован и снят до микрозадачи `.then` промиса
  регистрации, запись ожидающего спавна разрешается в уже несуществующий ref. При разрешении
  проверять `registry.get(id) === ref`; иначе считать спавн снятым (как событие `removed`).
- **A2A-5. Worker умер посреди consume.** Запрос, забранный (`consume`) агентом worker'а, но не
  отправленный, теряется. `consume` выдаёт аренду; успешная отправка её подтверждает; при выходе
  worker'а неподтверждённые аренды возвращают запросы в открытые.
- **A2A-6. Вечные входящие для агентов, которые не ответят.** Записи входящих запросов удаляются
  при снятии адресата из реестра и по сроку `a2a.replyTimeoutMs` (если `> 0`).
- **A2A-7. Сила тестов при отсоединённой отправке.** Тесты «ноль отправок» после перехода на
  отсоединённую отправку проверяют до её завершения. Дать тестам детерминированную точку
  ожидания (например, ожидание settle релея), без `sleep`.
- **A2A-8. Обрезка по UTF-16.** Капы текста в релее (`src/task/executor.ts` ~3335) и артефакте
  (`src/a2a/rpc.ts` ~255) режут `.slice` по code units и могут разрезать суррогатную пару.
  Использовать обрезку по code points (существующий помощник, если есть).

### Teams

- **T-1. Уведомление команды не закрывает открытый вопрос.** Сейчас уведомление записывается как
  обычная отправка, и `unansweredSends` считает вопрос получателя отправителю отвеченным.
  Уведомления (`teamNotice`) не меняют учёт ответов; они по-прежнему завершают `wait` адресата.
- **T-2. Уведомления не прерывают ожидание собственных задач.** `wait`, ожидающий конкретные
  фоновые задачи/сервисы, не прерывается уведомлением команды; уведомление ставится в очередь как
  обычное входящее и доставляется после. `wait` на ответы агентов прерывается как сейчас.
- **T-3. Пустая команда уходит в отставку.** Когда в поколении команды не осталось участников
  (handle-only stop последнего, release, удаление), поколение снимается, лид получает
  уведомление «команда `<name>` завершена: участников нет». Тогда защита лида от парковки
  перестаёт действовать. Whole-team stop без ack по таймауту не меняется: лид получает
  уведомление и решает (`--force`).
- **T-4. Одно idle-уведомление на ход.** Сейчас structured-участник даёт два: на текстовой
  остановке и после `yield` по напоминанию. Уведомление шлётся в момент окончательного простоя
  хода: после `yield`/`handback` или когда напоминания исчерпаны, а не на промежуточной текстовой
  остановке, за которой следует напоминание.
- **T-5. Граница `team.stopAckTimeoutMs`.** Диапазон 1000..2147483647 мс; значения вне
  диапазона зажимаются (схема настроек + рантайм).
- **T-6. Stop участника, прерванного до регистрации.** Если регистрация спавна провалилась, его
  ожидающий stop разрешается сразу («released: never registered»), лид уведомляется, таймаут не
  ждётся.
- **T-7. Тест handle-only stop прерванного участника** (ветка кода уже есть, теста нет).
- **T-8. Ревизия плана.** Каждая отправка плана увеличивает ревизию (в пределах поколения
  участника). Уведомления о плане показывают `rev N`. `/team approve <handle> [--rev N]` и
  `/team reject <handle> [--rev N] <reason>`: при указанной и устаревшей ревизии - отказ с
  текущей ревизией; без `--rev` - текущий план (как сейчас).
- **T-9. Код ошибки вместо текста.** Fallback холодного возрождения (`agent-session.ts`
  ~5785-5791) сравнивает текст ошибки worker-RPC. Ошибки рантайма команды получают поле `code`
  (`TEAM_STALE_GENERATION`, `TEAM_LEAD_GONE`), RPC переносит его, сравнение - по коду.
- **T-10. Гейт плана пропускает read-only `find` и `ast_grep`.** Allowlist гейта: `read`, `grep`,
  `glob`, `find`, `ast_grep`, `lsp` (без мутирующих действий), `web_search`, `wait`, записи
  `agent://`/`team://`, `yield`/`handback`. Только если в коде эти инструменты не пишут на диск.
- **T-11. Idle-уведомления не тратят бюджет участника.** Уведомления, созданные рантаймом от
  имени участника (idle, stop decline/timeout), не списываются с его IRC rate-бюджета; дедуп
  остаётся. Иначе idle-уведомление может отнять бюджет у отправки плана.

Не делаем (с обоснованием в документации, если её касается): дублирование decline-уведомления
и wake-relay лида (информация не теряется); расширения с именами встроенных инструментов
(вне модели угроз: расширения - код пользователя).

### Foundation

- **F-1. Дедуп поиска eval-инструментов.** Поиск описаний eval-инструментов
  (`describeEvalTools` и соседи) повторяется на каждый спавн; кэшировать в пределах сессии
  с инвалидацией при перестройке инструментов.
- **F-2. Тесты доступа на Windows.** Для `read`/`write` - тесты `/dev/null` и `NUL` (чтение
  пустое, запись успешна и ничего не создаёт). В `crates/pi-shell` тест stderr получает
  положительный контроль (stderr действительно пишет в fd 2, когда не перенаправлен).
- **F-3. Изоляция тестов.** Очистка poison-родителя после частичного setup; достижимость
  poison-предков на не-Windows покрыта тестом или явно помечена `skipIf`.
- **F-4. pi-builtins `cat`/`head`/`ls` с `/dev/null` на Windows** работают так же, как на POSIX
  (через общий маппинг `host_path`).

## Группа B. Тестовая инфраструктура

- **INF-1. Последовательный путь раннера не останавливается на первом падении.**
  `scripts/ci-test-ts.ts` в последовательном режиме (CI или `isCI()`) бросает на первом
  упавшем чанке. Он прогоняет все чанки и в конце выдаёт сводку упавших с ненулевым кодом,
  как параллельный путь. Выяснить, по какой переменной окружения `isCI()` срабатывает в
  агентской оболочке, и описать это в `docs` по тестам (`OMP_TEST_CONCURRENCY`).
- **INF-2. Одна версия Bun.** Дочерние `bun test` запускаются через `process.execPath`, а не
  через `"bun"` из `PATH`/`Path`. Раннер проверяет минимальную версию Bun из корневого
  `package.json` и падает с понятным сообщением. Пакетный `check:types`, рекурсивно
  вызывающий себя под Bun 1.3.14, получает такую же проверку.
- **INF-3. Тесты, нестабильные под нагрузкой:** `test/cli-provider-model-deferral.test.ts`
  (60 с таймаут), `test/settings-live-routing.test.ts`, `test/tools/browser-attach.test.ts`
  (`pickElectronTarget`), `test/tools/browser-storage-state.test.ts`. Каждый воспроизвести под
  16-поточной нагрузкой, убрать зависимость от времени стены (ожидание условия вместо таймера,
  перенос в heavy/singleton-бакет, если тест по природе тяжёлый).

## Группа C. Исторические падения Windows

Список - `.superpowers/sdd/2026-11-08-foundation-fixes/baseline-*.log` и
`.superpowers/sdd/2026-11-08-agent-teams-protocol/final-suite-coding.log` (UTF-16): 81 тест
coding-agent, 59 тестов `cargo test -p pi-shell`, 865 ошибок Clippy в `crates/pi-shell` на
Windows. Причины не разобраны, поэтому план C начинается с классификации: кластеры по причине
(сигнатура ошибки, общий модуль), для каждого - решение «чинить код / чинить тест / платформенно
неприменимо, `skipIf(win32)` с причиной». Clippy: сначала выяснить, гоняет ли upstream CI
Clippy под Windows; Windows-only предупреждения чинятся в коде под `cfg(windows)`, без глобального
ослабления линтов. Задачи исправления по кластерам дописываются в план после классификации и
утверждаются отдельно.

## Общие требования

- Bun 1.4.4 (`>=1.4.4`); на этой машине - явный путь к 1.4.4 первым в `PATH`/`Path`.
- Каждое изменение поведения - регресс-тест, падающий до правки и проходящий после.
- `bun check` пакета `coding-agent` зелёный; Rust - `cargo test -p pi-shell` без новых падений.
- Документация (`docs/a2a.md`, `docs/agent-teams.md`, `docs/settings.md`) и `[Unreleased]` в
  `packages/coding-agent/CHANGELOG.md` обновляются в задаче, которая меняет поведение.
