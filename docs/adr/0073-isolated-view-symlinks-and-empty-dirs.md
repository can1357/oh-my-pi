Terms. **View**: the isolated root `create_worktree` builds for a subagent. **Manifest**: the content-addressed blob `snapshot_at` writes; a merge compares two of them. **Kind**: regular file, directory or symlink. **Escape**: a symlink whose target is absolute, leaves the workspace root, or reaches outside it through another link. **Confirmed absence**: `lstat` finds nothing at a path, and no ancestor of the path exists as a link or as a non-directory. `lstat` does not follow links, and a missing ancestor is fine: a deleted directory deletes the files under it.

## Context

### What the code does today

- **The walk sees every kind and keeps one.** `snapshot_at` walks with `.hidden(true).gitignore(true).skip_git(true)` in `WalkOrder::Path` (`operations.rs:1034-1039`). The walker's default filter accepts every kind (`crates/walker/src/lib.rs:184-188`, `:225-234`, `:299-303`), `FileType` has `File`, `Dir` and `Symlink` (`crates/walker/src/lib.rs:54-61`), and links are not followed by default (`:549`). They are classified without being followed (`:1872-1878`, `:2341-2352`). The sink returns early unless `entry.file_type == FileType::File` (`operations.rs:1052-1058`). A symlink or a directory never reaches the manifest.
- **The manifest has no kind.** `ManifestEntry` is `{ path, mode, hash }` (`operations.rs:312-316`). The bytes are the magic `OMPWS2\0` (`:52`), a `u32` prefix count and the prefixes, then for each file a length-prefixed path, a `u32` mode masked to `0o7777` and a 32-byte content hash, in walk order (`:1041-1066`). `parse_manifest` accepts exactly that magic and rejects a mode above `0o7777` (`:1807`, `:1842`). The magic has never changed: `git log -S'OMPWS2' -- crates/envd` finds only the commit that introduced it, `8e3f027aae`, and `-S'OMPWS1'` finds nothing. There is no earlier version and no compatibility reader.
- **The snapshot id is the manifest hash.** `snapshot_id` and `tree_hash` are the hash of the manifest blob (`:1084-1096`), so any change to the manifest bytes changes the id of an unchanged tree. A `CreateWorktree.base` taken before such a change is refused (`:684-692`). The driver passes none (`spawn.rs:1025`).
- **The view copies files only.** For each manifest entry `create_worktree` joins the path, `canonicalize`s it, returns `OutsideRoot` if the canonical path leaves the root, creates the parents, then `clone_file_cow`s and `set_mode`s the file (`:709-727`). The loop cannot carry a link: it would follow a symlink entry and clone the target's bytes as a file, or fail with `OutsideRoot` (escaping) or `NotFound` (dangling). Because the walk never yields a link, that `OutsideRoot` is reachable only through a race between the walk and the copy [INFERENCE]: `create_worktree` replays a manifest it has just walked (`prepare_isolation_baseline` only size-checks the untracked set, `:440-467`). `hash_file` is fail-closed: it opens with `O_NOFOLLOW` and returns `OutsideRoot` for anything that is not a regular file (`:1182-1191`, `:1977-1984`).
- **Parent writes follow links.** The merge opens each path through the document authority (`operations.rs:1246-1247`). That authority resolves a path's parent with `canonicalize_existing`, which follows symbolic links (`fs.rs:1616-1626`, `:1656-1700`). So a file the child creates under a path the parent holds as a link is written where the link's target points, as long as the target resolves inside the root.

### What goes wrong today

1. **Tracked symlinks are missing from the view.** ADR 0007 defines the view as "every tracked file plus every untracked file that is not gitignored" (`docs/adr/0007-subagent-filesystem-isolation.md:26-29`). A tracked symlink is a tracked file and is absent. This checkout tracks none (`git ls-files -s` lists no mode `120000` entry; the count on 2026-11-15 is 0). ADR 0040 says "the tree tracks none today" (`docs/adr/0040-remote-build-and-test-execution.md:743`). So the gap has no victim here, but it bites repositories that track links.
2. **A child's links and empty directories never come back.** The merge snapshots the view with the same walk (`operations.rs:805`), so they are in neither the child manifest nor the diff artifact.
3. **A base file the child stops reporting is merged as a delete.** [READ, not exercised] A file the child replaced with a link or a directory is absent from the child manifest. `merge_target` sees base present, child absent and parent unchanged, and removes it from the target (`:1531-1535`). `plan_restore` plans a `Delete` (`:1262-1275`), and `apply_restore_plan` commits it (`:1359-1390`). The driver's defaults are apply and patch (`settings.rs:293-294`, `:393-396`; used at `spawn.rs:1042-1080`), so on the default path the parent's file is deleted with no conflict. The same happens when the child's own `.gitignore` edit hides a base file (`operations.rs:1034-1037`): the walk stops reporting it although it is still on disk in the child (O8). Both are one defect, and D8 closes both in S1.
4. **The clean check cannot see them.** `destroy_worktree` without `force` compares manifest entries (`:764-773`), so a view holding only new links or empty directories counts as clean and is removed. The driver passes `force: true` (`spawn.rs:1096-1098`), so only other callers reach this. S3 closes it: once manifests carry kinds, the same comparison sees them.
5. **Empty directories are not git content**, so a git worktree loses them too, and the view loses the untracked, unignored ones. On 2026-11-15, outside `.git` and `node_modules`, this working tree holds 3665 empty directories, and all 3665 are gitignored (`git check-ignore`). None is a victim here.
6. **An escaping symlink is real in this project.** ADR 0040 records an untracked, unignored `vendor` symlink to the main checkout's `vendor/` in nearly every `omp2-wt-*` worktree (`docs/adr/0040-remote-build-and-test-execution.md:743-747`). A view built from such a worktree must not fail, and must not carry that link to the child.

### Rules that bind

- **ADR 0007 has no sentence about symlinks, canonical paths or leaving the root.** Searching the file for those words finds none. The rules that govern an escape are its isolation rules: "The child MUST NOT share the parent's mutable authority. It never writes into the parent's tree; it writes into its view." (`docs/adr/0007-subagent-filesystem-isolation.md:37-38`); "The copy fallback never shares a writable inode with the parent." (`:32-33`); "Prohibited: children spawned with direct write access to the parent workspace when isolation is available." (`:53-54`). A link in the view that resolves into the source tree, or anywhere outside the view, is a path for the child to write outside its view. The code enforces this with `OutsideRoot` (`operations.rs:718-720`) and `hardlink_copy_fallback` (`:2110-2128`; its comment at `:2111-2113` states the rule).
- ADR 0071 applied the same reason to carried caches: a link with an absolute target inside the canonical source root removes the whole carried directory as `AliasesSource`, "because writes through such a link would change the source checkout" (`docs/adr/0071-subagent-isolation.md:56`), while "a relative symlink is carried as is" (`:68`).
- `crates/core/src/project_file.rs:6-9`: contained reads accept a symlink that stays inside the root and refuse one whose canonical path leaves it.
- Input capture (ADR 0040 Part D): a tracked symlink refuses the capture, and an untracked one is skipped and counted (`operations.rs:953-962`).
- A format change "changes manifest content (`MANIFEST_MAGIC`, `:52`) and persisted snapshots, so it needs the owner under additive-only" (`docs/research/subagent-isolation.md:200`).

## Decision

**Answer to ADR 0071 O4: fix the view first, guard the merge now, and change the format last.** Four slices fix it, and only one of them changes the format. S1 guards the merge with no format change. S2 makes the view faithful for leaf directories and in-root links, reading them from the walk, again with no format change. S3 records kinds in the manifest (owner O1). S4 merges by kind. The pin test is ignored until S2 (D10). This record and the test are S0.

Scope of the rules: D2 to D7 describe Unix. D8 applies on every platform. D9 says what Windows keeps.

- **D1. Order of work.** S0 is this record and the pinned test, ignored. S1 is the kind guard D8, with no format change (owner O2). S2 is view-only replay of leaf directories and in-root links, with no format change (owner O9); it removes the pin test's ignore attribute. S3 records kinds in the manifest as OMPWS3 (owners O1 and O7, in that order). S4 merges by kind (owners O1, O4, O5 and O10). S5 writes the documents.

- **D2. Kinds and format (S3).** The snapshot manifest MUST be able to represent a regular file, a directory and a symlink. S3 moves snapshot manifests to `OMPWS3\0`. No earlier slice changes the manifest.
  - **Layout.** After each path comes one kind byte. Kind 0 is a file, followed by a `u32` mode and a 32-byte hash as in `OMPWS2`. Kind 1 is a directory with no payload (D5). Kind 2 is a symlink, followed by its target in the length-prefixed encoding paths use (`write_bytes`, `operations.rs:1855`). Prefixes are unchanged. Files and directories are written in walk order, then links in walk order, because classifying a link needs every link (D3). One tree has one byte string.
  - **Reader.** It MUST keep accepting `OMPWS2\0` and read it as files only. It rejects an unknown kind byte, an empty target, a target containing NUL, and any entry that takes the manifest past `MAX_MANIFEST_BYTES` (`check_manifest_bound`, `operations.rs:1888`).
  - **Capture.** Input-capture manifests MUST stay `OMPWS2\0` and files only (ADR 0040 Part D). The single `MANIFEST_MAGIC` constant (`operations.rs:52`) therefore splits: a capture constant keeps the old bytes, and the snapshot constant moves. The driver decoder (`exec_composer.rs:338`) keeps checking the capture bytes.
  - `files` keeps meaning regular files.

- **D3. Symlinks: classification.** A symlink is recorded with its raw target. It is NEVER dereferenced, hashed, read at replay time or cloned. A view recreates a link with the same spelling only when the target is relative, valid UTF-8, free of NUL, not empty, and its lexical resolution from the link's parent directory stays inside the root.
  - **Scan.** The target's components are scanned left to right against the full set of symlink entries, with names matched after folding case and Unicode normalization; matching too much only omits more. An intermediate prefix that is a symlink entry makes the target `via-symlink`. `..` pops a prefix only when that prefix is not a symlink, and popping above the root is `escapes-root`.
  - **Chains and cycles.** A final component that is itself a link is followed: the scan continues with that link's target. When the scan meets a link it has already visited, it has found a cycle. A cycle is recreated, because nothing in it can leave the root, and the kernel reports `ELOOP` on use. A chain of more than 32 distinct links is `via-symlink`. The bound of 32 is this record's choice [INFERENCE: the kernel's own limit differs by platform, 32 on Darwin and 40 on Linux]. A chain that ends in an omitted link or in an escape is `via-symlink`.
  - **Omitted and reported.** An unsafe link is omitted from the view and reported with its path and one reason: `absolute`, `escapes-root`, `via-symlink` or `unrepresentable`. A target that is not UTF-8, contains NUL or is empty is `unrepresentable`. Omission is never an error, so a view still builds from a worktree like the `vendor` one above. An absolute target is omitted even when it points into the source root, because in the view it would alias the parent's tree (ADR 0007:37-38; ADR 0071:56).
  - **Dangling and directory links.** A dangling link whose target stays inside the root is recreated; classification is lexical because `canonicalize` fails on it. A link to a directory is a symlink entry, and the walk does not descend into it.
  - **The view's base.** Until S3 the base is the file manifest, which holds no links. From S3, `create_worktree` writes a derived manifest, the snapshot minus omitted entries and the reserved name, as its own blob, and records its id as the base (`WorktreeRecord.base`, `operations.rs:253-260`; set at `:732`). The parent's own snapshots keep every entry, so restore can still see them.

- **D4. Replay.** A view is built in this order: directories (D5), then files as today (`create_dir_all` for the parents), then links. Before each link is created, every ancestor of its destination is `lstat`ed and must be a real directory inside the view. In S2 the targets come from the walk, which reads each link with `read_link` when it visits it. In S3 they come from the derived manifest. In both, a symlink entry MUST NOT reach `canonicalize`, `clone_file_cow` or `set_mode`, and no target is resolved at replay time. The `set_mode` that follows each commit (`operations.rs:1393-1399`) MUST NOT follow a link: `set_mode` does (`:2028-2032`). The reserved name `.omp-isolation-owner` (`:295`) is skipped for every kind. From S3, `parse_manifest` MUST reject a manifest in which a file or link path is a proper ancestor of another entry, and the merge target MUST pass the same check before anything is applied (S4). Replay never reads a live link (D3): in S2 a link's target is the one the snapshot walk read, and in S3 the one the manifest records. `create_worktree` takes the snapshot and builds the view in one call (`operations.rs:681-727`), so no caller can change the tree in between. S2 therefore adds a test-only seam between the snapshot walk and link replay. Its test re-points the live link inside the seam and expects the walked target in the view; it fails only if replay reads the live tree. S3 keeps it passing while the targets come from the manifest. Regular files keep today's replay from the live tree (`canonicalize` at `operations.rs:717`, the root check at `:718`, the clone at `:725`); that race is not fixed here (O11).

- **D5. Directories.** A leaf directory is one whose next visited entry in the pre-order walk (`crates/walker/src/lib.rs:589-593`; `WalkOrder::Path` at `operations.rs:1039`) is not beneath it, after filtering. Leaves are recreated, so a directory whose files are all gitignored is carried empty. ADR 0007's rule that gitignored files are not copied is unchanged.
  - **No directory mode is stored, compared or applied in this record.** Every directory is created with the default mode, as parents are today (`create_dir_all`, `operations.rs:723`). Whether to record modes, for leaves or for every directory, is O7. It must be answered before S3, because it changes the directory entry (D2).
  - For kind comparisons (S4), a path is a directory when it has a directory entry or any entry beneath it, so a file replaced by a directory with children is a kind change although only leaves are stored.
  - ADR 0007:31 says "The view is created per file." D5 amends that for directories, which are made with `mkdir` and never cloned. S5 writes the amendment.

- **D6. Merge-back (S4).** Entries compare by kind and payload: a file by mode and hash, a symlink by target, and a directory by existence (D5). The three-way merge stays per path.
  - **Order of checks.** For each path the merge would write, a child link is classified first with D3, against the whole merge target (the child's changes laid over the parent's current tree). An escape or an absolute target is `OutsideRoot` whatever the parent holds; a `via-symlink` result is also `OutsideRoot`; `unrepresentable` is `PathChanged`. Then a target that is not in normal form (any `.`, `..` or empty component) is `PathChanged` with detail `unverbatim`, because `CreateSymlink` rebuilds the spelling (`fs.rs:1427-1438`; O5). Only then does the three-way compare apply, which yields `PathChanged` when both the child's change and the parent's change differ from the base.
  - **Kind changes.** A kind change against the base, in any pairing of file, directory and symlink, is `PathChanged` and is never planned as a delete.
  - **Omitted links stay.** The parent keeps the links the view omitted. They are not in the view's base (D3), so their absence from the child is not a deletion.
  - **Physical check.** The parent's manifest lists neither links nor ignored paths, so before a symlink is applied its target is resolved on disk in the parent, one component at a time with `lstat`. A final-component link is followed with `readlink` under the same 32-link bound. An intermediate link, or any link on the chain that fails D3, is `OutsideRoot` (`via-symlink`). The filesystem may fold case (APFS does by default [INFERENCE]), so the check compares names as the filesystem resolves them.
  - **Directories.** A new directory is created with `mkdir`. A base directory the child removed is removed with `rmdir` only when it is empty in the parent. If the parent has gained entries, that is `PathChanged`, not a deletion.
  - **Order and re-check.** Creates apply parents first (directories, files, then links). Deletes apply children first (links and files, then directories, deepest first). Immediately before each plan, under the workspace lease, the destination's ancestors are `lstat`ed again and compared with the kinds the plan was made against. The lease covers the plan's own paths, not their ancestors (`operations.rs:1288-1305`; `document.proto:1164-1172`), so this check narrows the window and does not close it (O10). A mismatch is `ModifiedAfterSnapshot` (`env.proto:1099-1100`).
  - **Failure and result.** A merge apply is not atomic. It stops at the first failure, and plans that already committed stay committed (`operations.rs:881-890`). The apply never undoes them itself: there is no automatic rollback (item 3). The pre-apply parent snapshot, published at `operations.rs:849`, is the recovery point: restoring it returns the parent to its state before the merge. The merge result MUST name that snapshot and the plans that committed (O4), and S4's exit test MUST exercise a failure part-way through the apply. The artifact becomes `OMPWSD2` with kind-tagged records.

- **D7. Legacy manifests.** A legacy `OMPWS2` manifest holds files only.
  - **Restore (S3).** Against a legacy target, restore compares file entries only and deletes no link or directory (`plan_restore`'s delete loop, `operations.rs:1262-1275`; `unchanged_entries`, `:1748-1754`). From S3, restore compares the file projection of any manifest; restore by kind is S4.
  - **Merge (S4 only).** Until S4, merges compare the file projection and create nothing for directories or links (S2 and S3). From S4, against a legacy base the base's links and directories are empty: a child's link or directory merges as a new entry, a link or directory the parent already has is never deleted, and a different one at the same path is `PathChanged`.
  - **Destroy (S3).** `destroy_worktree` compares file entries only against a legacy base (`operations.rs:764-773`).
  - **Why the reader stays.** Journaled snapshot ids (`rewind-checkpoint` nodes, `dispatch.rs:669-706`) and persisted worktree bases outlive binaries, so the legacy reader is mandatory. A binary older than S3 that reads an `OMPWS3` manifest fails closed with `manifest magic mismatch` (`operations.rs:1807`).

- **D8. Kind guard (S1 through S4, every platform).** The checks use `lstat` on the live child and parent roots when a merge is built. They read no manifest kinds, so they hold in every slice from S1 to S4. The create rule below gates S1 to S3; from S4 it applies only where the child's entry differs in kind from the parent's ("Semantics by case").
  - **Delete needs confirmed absence.** A base file that the child manifest lacks is planned as a delete only when its path is confirmed absent in the child root. Otherwise it is a `PathChanged` conflict, and nothing is deleted at that path. That covers a directory or a symlink at the path, an ancestor that exists but is not a real directory, and a regular file the child's ignore rules hide (O8).
  - **Create needs a free slot.** A path the merge would write is a `PathChanged` conflict when the parent root holds a symlink or a directory at it, or holds an ancestor that exists and is not a real directory. A regular file at the path is not a conflict under this rule: the three-way rule decides. This rule closes the write-through described in Context (`fs.rs:1616-1626`). From S4, a child link or directory at a path where the parent holds the same kind is not a create: the three-way compare in "Semantics by case" decides it. A write below a parent link or file stays a conflict in every slice.
  - **Conflicts block the apply.** Any conflict stops the Patch apply before it starts (`operations.rs:848`), so D8 never leaves a partial apply behind.
  - **Tests.** Each slice from S1 to S4 names the tests it adds. S1 names six (Slices).

- **D9. Windows.** Windows keeps today's view: no link and no leaf-directory replay in S2 or S3, both of which are `cfg(unix)`. D8 is not waived: its `lstat` checks run on every platform, so file-to-link and file-to-directory conflicts apply there too. Recording and replaying links and directories wait for Windows CI (ADR 0071 O7). A tracked symlink is dropped from a Windows view without a failure, as today.

- **D10. The test.** `isolated_view_keeps_empty_directories_and_in_root_symlinks` in `crates/envd/tests/workspace_capture.rs` pins D3 to D5 for the in-root cases. It is a view test and never calls merge: it does not pin item 3's data-loss defect, which S1's six tests pin, each run against the unfixed merge first (O12). It is `#[cfg(unix)]`, so it pins nothing on Windows (D9). It is **ignored until S2**: `#[ignore = "ADR 0073 S2: the view does not replay links or leaf directories yet"]`. This is the recommended answer to O3. S0 merges the attribute, so the suite stays green, and S2 removes it in the same change that makes the test pass. The test lives in `crates/envd/tests/` because that is the owning seam (`AGENTS.md:808-809`), and `workspace_capture.rs` is the only file there that builds `WorkspaceOperations` (checked by grep). The repository's ignore precedents carry a reason string (`crates/walker/tests/perf.rs:29`, `crates/exec-reapi/tests/live_buildbuddy.rs:231`).

### Semantics by case

| Case | View | Merge through S3 | Merge from S4 |
|---|---|---|---|
| Symlink, relative target, resolves inside the root | recreated with the same spelling, after the directories and files (D4) | not merged: the file projection holds no links; D8 still runs | compared by target; applied as a link; classified again on the merge target (D3, D6) |
| Symlink, relative target that leaves the root | omitted, reported `escapes-root` | not merged; nothing written | child-made: `OutsideRoot` conflict, never applied |
| Symlink, absolute target, even into the source root | omitted, reported `absolute` | not merged | child-made: `OutsideRoot` conflict |
| Symlink with a link as an intermediate component | omitted, reported `via-symlink` | not merged | child-made: `OutsideRoot` conflict |
| Final component is a link that is omitted or escapes, or a chain over 32 links | omitted, reported `via-symlink` | not merged | child-made: `OutsideRoot` conflict |
| Dangling link, target inside the root, normal form | recreated (classification is lexical) | not merged | applied as a link; `PathChanged` with detail `unverbatim` when the target has `.`, `..` or an empty component (D6, O5) |
| Chain inside the root, or a cycle | recreated; a cycle gets `ELOOP` on use | not merged | applied under the same normal-form rule |
| Target not UTF-8, containing NUL, or empty | omitted, reported `unrepresentable` | not merged | `PathChanged` conflict with detail |
| Symlink to a directory | recreated as a link; the walk does not descend | not merged | applied as a link |
| Leaf directory | recreated with the default mode, before the files (D4, D5) | not merged; no directory is created or removed | `mkdir` when new; `rmdir` only when empty (D6) |
| Kind change against the base (file to link, file to directory, link or directory to file) | not applicable | `PathChanged` conflict from S1 (D8); nothing deleted or written there | `PathChanged` conflict; never a delete (D6) |
| Base file the child lacks, path confirmed absent | not applicable | deleted, as today (D8) | deleted, as today |
| Base file the child lacks, path present on disk, or an ancestor that exists but is not a real directory | not applicable | `PathChanged` conflict from S1 (D8); nothing deleted | `PathChanged` conflict |

| Child creates a link or directory where the parent has one | not applicable | not merged | three-way compare by target or existence; `PathChanged` when the parent differs |
| Reserved name `.omp-isolation-owner` | never in the view | never merged: the walk skips it in an isolated walk (`operations.rs:1054`) | never merged |

| **A.** Defer and document only. | Rejected as the end state: it leaves the data-loss path (item 3). Accepted for S0, which records and pins the gap. |

## Consequences

- Views become faithful for tracked symlinks and leaf directories from S2. From S1, a file can no longer be deleted or written through a link that the child or the parent holds.
- Prohibited: dereferencing a symlink into a view; recreating an absolute or escaping link; planning a delete without confirmed absence; creating a file under a parent link or directory at that path; applying a mode through a link; comparing a legacy manifest for kinds it cannot represent; and a merge that writes a link whose spelling it cannot keep.
- Costs accepted: until S4, links and directories a child creates or deletes never reach the parent, as today. S2 changes what the view holds, not what the patch carries. The S3 format change is one-way: a binary older than S3 fails closed on `OMPWS3`. Manifests grow by one entry per leaf directory and symlink, inside `MAX_MANIFEST_BYTES` (`operations.rs:55`). The wire gains additive fields (O4). The pin test stays ignored until S2.
- Not decided here: directory modes (O7); recording every directory; hard links, FIFOs and sockets (the walker already skips them, `crates/walker/src/lib.rs:2349-2351`); the file-copy race (O11); the lease window (O10).
