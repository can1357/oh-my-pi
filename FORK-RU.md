# omp-fork: полное руководство по функциям и возможностям

**Форк:** `spgsroot/oh-my-pi-team-agents` (main `a1d33f5`), база — upstream `can1357/oh-my-pi` 18.16+
**Установка на этой машине:** команда `omp` указывает на форк-бинарник
(`~/.bun/bin/omp → ~/.local/lib/omp-fork/omp-launcher.sh → ~/.local/lib/omp-fork/omp`).
Профиль — штатный `~/.omp` (ваши модели, skills, MCP — всё как было).
**Откат на оригинальный omp:**
```bash
ln -sf ../install/global/node_modules/@oh-my-pi/pi-coding-agent/dist/cli.js ~/.bun/bin/omp
```
**Обновление форк-бинарника после правок в рабочей копии:**
```bash
cd <путь-к-клону> && bun run build && rsync -a packages/coding-agent/dist/omp ~/.local/lib/omp-fork/omp
```

## 1. Межтерминальное взаимодействие агентов (A2A-мост)

Агенты в **разных терминалах/сессиях** обмениваются сообщениями и статусами по протоколу
A2A v1.0 (Linux Foundation): JSON-RPC 2.0 поверх HTTP, SSE-стриминг, AgentCard.
Локальные сабагенты одной сессии общаются через `write agent://<id>` (только
локальные агенты); чужие терминалы достигаются **только** спавнами `a2a:` через
task tool.

### Терминал-сервер

**Мост включён по умолчанию** (`a2a.enabled: true`, `a2a.port: 0`): каждый запуск
omp автоматически поднимает мост на свободном порту 127.0.0.1 - никаких флагов не
нужно. Отключение: `a2a.enabled: false`; фикс. порт: `omp --a2a-port 7601`.

**Имя терминала**: при пустом `a2a.name` и без `--a2a-name` генерируется
skill-id-safe имя `<slug(basename(cwd))>-<pid>`. Настроенное или автоимя
используется как id главного навыка карточки, имя записи локального моста и
имя отправителя; у соседей оно доступно как `a2a:<имя>`. То же имя служит
алиасом для адресации Main (`to`, `GetTask`, `CancelTask`), но не разрешает
его отмену: `CancelTask` отклоняет отмену Main и по этому алиасу. Значения
«по умолчанию Main» нет.

- Мост слушает **только 127.0.0.1** (извне недоступен);
- bearer-токен: `<agent dir>/a2a.token` (создаётся автоматически, права 600);
- карточка агента: `GET http://127.0.0.1:<port>/.well-known/agent-card.json` -
  имя, навыки (живые агенты сессии), capabilities и `instanceId`.

### Реестр мостов и авторегистрация

Каждый мост пишет **один файл на процесс**
`~/.omp/agent/a2a-bridges/<pid>.json` атомарно (tmp + rename): `pid`, `port`,
`name`, `startedAt`, случайный `instanceId`. Читатели перечисляют каталог,
проверяют живость pid, удаляют мёртвые записи, а при регистрации сверяют
`instanceId` из карточки на этом порту (защита от переиспользования pid). При
остановке мост удаляет свой файл. Старый формат `a2a-bridges.json` не читается и
не пишется; одновременная регистрация двух процессов не затирает друг друга.

**Авторегистрация включена по умолчанию** (`a2a.autoRegister`): при старте сессии
omp находит все живые мосты, кроме себя, и регистрирует их соседей. Повторная
регистрация того же URL **заменяет** его записи (никаких `Main-3`-дублей); разные
URL с одинаковым именем получают суффиксы `-2`/`-3`.

**Симметричное обнаружение**: терминалы, запущенные позже, видны по требованию -
голое `read agent://` (ростер) или спавн неизвестного `a2a:` имени запускает
debounce-рескан (>=2 с): новые пиры регистрируются, пропавшие мосты удаляются из
ростера. Ручные команды остаются:

```bash
/a2a auto          # перерегистрировать все живые мосты вручную
/a2a add http://127.0.0.1:7601 --token $(cat ~/.omp/agent/a2a.token)
/a2a list
/a2a remove <name>
```

При общем профиле все терминалы делят один токен, `--token` не нужен. Каждый
навык чужой карточки становится спавнимым агентом `a2a:<имя>`, кап
`a2a.maxPeerSkills` (default 8) режет ростер, main идёт первым.

### Общение

**Канал ответа**: адресный запрос получает конверт с указанием ответить
спавном `a2a:<имя-отправителя>` и сообщением об автоматической корреляции.
Когда task tool отправляет сообщение пиру, от которого есть неотвеченный
запрос, он автоматически ставит `metadata.inReplyTo = <messageId запроса>`
и снимает этот запрос с ожидания. Ответ помечается как ответ на запрос и не
получает нового конверта, поэтому бесконечной цепочки запрос->ответ->запрос
нет. Батчевый `context` пробрасывается в удалённый спавн;
в plan mode любой `a2a:` спавн отклонён (удалённый терминал нельзя удержать
read-only).

В клиентском терминале просто просите модель:
> «Спавни a2a:<имя-пира> с промптом: как дела у тебя в терминале?»

Запрос уходит в живую сессию терминала-пира и попадает в его основную беседу.
Спавн завершается подтверждением доставки; коррелированный ответ приходит
позже отдельным спавном от пира. Статусы задач: SUBMITTED -> WORKING ->
COMPLETED/FAILED (TASK_STATE_*); пендинг-спавн с 30-сек grace, INPUT_REQUIRED
вернёт «waiting for input».

### Что видит внешняя сторона (JSON-RPC)

`GetTask`/`ListTasks` показывают состояние задач: running->WORKING,
idle+завершён->COMPLETED/FAILED (по output-артефакту), parked->WORKING,
aborted->CANCELED/FAILED; advisor скрыты. `ListTasks` сохраняет клиентский
`message.contextId` для задач, созданных `SendMessage`, фильтрует по нему,
страницы стабильны (порядок создания/id), пустой `pageToken` = первая страница.
Запросы без `id` - уведомления (обработать, HTTP 204 без тела); батч-массивы
возвращают массив ответов без уведомлений. `CancelTask` отменяет только задачи,
созданные через этот мост; Main и локальные сабагенты -> `TASK_NOT_CANCELABLE`,
терминальность перепроверяется после abort.

`a2a.clientTimeoutMs` ограничивает **весь** удалённый спавн (первый `SendMessage`
+ все `GetTask`) одним общим сигналом; connect-таймаут остаётся 10 с на запрос.

### Схема «6 терминалов»

Да, работает: 6 терминалов, каждый `omp --a2a-port 760X`. Создавать агентов/
команды нужно сразу спавнами task tool (или `/team`), внешний терминал - только
если доступен соответствующий terminal-тул; жёсткой команды `orca terminal split`
в промпте больше нет. Пример с именами T1..T6:

| Терминал | Команда | Роль |
|---|---|---|
| T1 | `omp --a2a-port 7601` | «координатор»: добавляет всех остальных |
| T2-T6 | `omp --a2a-port 7602..7606` | исполнители |

В T1:
```bash
/a2a auto   # зарегистрирует T2..T6 разом
```
Появятся `a2a:<имя-T2>`, `a2a:<имя-T3>`, ... - имена берутся из настроенного
`a2a.name` или авто-имени `<slug(basename(cwd))>-<pid>`, а не из роли; `/a2a list` показывает
соответствие имя->URL. Дальше T1 раскидывает задачи параллельно (task tool умеет
несколько спавнов за один ход), агенты отвечают каждый из своего терминала.
Все терминалы делят один токен (общий профиль `~/.omp`). Терминалы-исполнители
также могут добавлять друг друга - граф любой.

Статусы транслируются: карточка каждого терминала содержит только **main +
работающих (running)** агентов - завершённые сабагенты (idle/parked) не попадают
в карточку, чужие ростеры не засоряются мёртвыми записями (`ImplTask*`,
`Review*`); завершённый агент по-прежнему доступен по id.
«Кто чем занят» видно через `read agent://` и карточку в любой момент.

## 2. Браузер в вашем реальном Chrome (browser relay)

`browser.relay: true` — встроенный тул `browser` (eval) водит вкладки вашего
реального Chrome (с логинами и расширениями) через relay-расширение:

```bash
bun packages/coding-agent/dist/omp browser-relay install   # запишет extension в ~/.omp/browser-relay/extension
omp config set browser.relay true
# затем руками: chrome://extensions → Developer mode → Load unpacked →
#   ~/.omp/browser-relay/extension  (badge «on» = подключено к relay :9224)
```

Relay-сервер (:9224, CDP-прокси) поднимается omp автоматически при первом
`browser.open`. Расширение — тонкий прокси: `attach`/`detach`/`send` (любая
CDP-команда) + tab-менеджмент, вся логика инструментов (observe, screenshots,
cookies, route/HAR, record mp4/webm, pdf, dialogs, vitals, react*) живёт в
харнессе поверх Puppeteer. Обход без расширения — managed-режим:
`app: {path: "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"}`.

**Грабли версий**: relay-сервер, extension и харнесс omp обязаны совпадать
(проверка семвера в обе стороны: «relay out of date» / «extension is out of
date»). На этой машине два omp — глобальный 18.10.1 (харнесс терминалов) и
форк 18.16.0 (alias `omp`); extension ставить бинарником того omp, что гоняет
ваши сессии. Расширение не умеет обновляться само при загрузке из копии —
авто-update только у установленного в `~/.omp` (файл stamp'ится версией).

История: до 2026-11-06 использовался chrome-mcp bridge (mcp-chrome-2026, 84
инструмента `chrome_*`, native messaging :12306) — удалён с рабочей машины
(759M+1G); `browser.chromeMcp` (default on) остаётся в форке для автодискавери
сторонних bridge'ей, но у нас моста нет и настройка ни на что не влияет.

## 3. Защита обмена между агентами (ingress-guard IrcBus)

Для сообщений `agent://` между агентами одной сессии (сабагенты, спавны):
- **rate**: 30 «токенов» (симв./4) на отправителя за 500 мс; **одно сообщение
  любого размера всегда проходит**, следующие в том же окне режутся;
- **dedup**: повтор того же текста тому же адресату в течение 30 с — отказ;
- **hops**: цепочка пересылок >28 — отказ (расширяют только wake-relay);
- **backpressure**: очереди aside/interrupt ≤50, избыток отбрасывается.
Настройки: `irc.ingressGuard` (on), `irc.rateLimitTokens` (30),
`irc.dedupWindowMs` (30000), `irc.maxHops` (28). Все отказы — тихие receipt'ы,
не исключения.

## 4. Отказ вместо очереди при перегрузе спавнами

`task.concurrencyPolicy: "refuse"` (default "queue") — при исчерпании
`task.maxConcurrency` спавн возвращает модели внятную ошибку:
`Concurrent subagent limit reached (N running; task.maxConcurrency=L). Do not
retry; wait for running tasks or ask the user to raise task.maxConcurrency.`
Лимит действует на **все** пути спавна: task tool, `/a2a` (внешние),
`pi.spawnSubagent` (расширения), workflow `agent()`.

## 5. Токен-бюджет сабагентов и инструмент handback

- `task.tokenBudget` (0=off): на 50% бюджета агенту в контекст инжектится
  `<total_tokens>N tokens left of M</total_tokens>`, на 90% — подсказка
  завершаться. Выживает у воскрешённых (wake/restore/revive) агентов.
- **handback**: для сабагентов без структурной схемы (`output`) регистрируется
  инструмент финального отчёта — обёртка над yield с фреймом «model output, not
  user text» и защитой от инъекций harness-тегов; один вызов на запуск.

## 6. Workflow — детерминированная JS-оркестрация

Инструмент `workflow({script, resumeFrom?})`:
```js
// script — тело async-функции с контекстом:
const audit = await agent("проверь аудит логов");
const results = await parallel([u1, u2, u3], u => agent(`обработай ${u}`), { concurrency: 2 });
phase("отчёт");
log("готово", results.length);
return audit.result;
```
- `agent(prompt)` — спавн сабагента (с общим лимитом concurrency!);
- `parallel(items, fn, {concurrency})`, `pipeline`, `phase`, `log`, `clock`, `args`;
- **детерминизм**: `require`/`import`/`Date.now`/`Math.random`/`eval`/`process`
  запрещены (внятные ошибки), песочница — allowlist глобалов, синхронный
  таймаут 30 с, отмена по AbortSignal;
- **journal + resume**: каждый вызов агента пишется в журнал сессии; после
  Ctrl-C/убийства `resumeFrom` повторно использует совпавший префикс и
  докручивает только хвост; упавший потомок фиксируется как `failed` и
  перекручивается на resume.

## 7. Capability-токены на деструктивные операции

Одноразовые токены `<8hex>@<id>`, TTL 10 минут. Деструктив (удаление worktree
с несохранёнными изменениями, `proc://<id>/kill` с несохранённым выводом) при
первой попытке возвращает ошибку **с токеном**; повтор с `force: "<token>"`
исполняет. Интерактивные kill в UI не гейтятся.

## 8. Шов для расширений: pi.spawnSubagent

Расширения теперь могут спавнить сабагентов:
```ts
export default function (pi) {
  pi.spawnSubagent({ agent: "scout", prompt: "найди X" }).then(ref => ...);
}
```
Права обычного сабагента, общий лимит concurrency. (Кандидат на PR в апстрим.)

## Прошитое знание сети (31b752b)

Системный промпт любой сессии с зарегистрированными a2a-пирами несёт секцию
**Peer network** (кто такие `a2a:`, имя = настроенное/авто, коррелированный ответ
через `metadata.inReplyTo`, `read agent://` для ростера и рескана,
`write agent://` только для локальных агентов) + **Orchestration protocol** (5
шагов: декомпозиция юнитов/волн -> действие-важнее-исследования -> диспатч одной
волной по именам -> трекинг без поллинга (инструкции GetTask больше нет) -> слияние
после волны). Внешний терминал создаётся только при наличии terminal-тула;
жёсткой команды `orca terminal split` в промпте нет.
Промпт каждого сабагента листает доступные ему a2a-пир терминалы — сабагент
может делегировать чужому терминалу сам, без переобъяснения.

## 9. Команды агентов (Agent Teams)

`.omp/teams/<имя>.md` - декларативная команда: members (ссылки на
agent-definitions + хэндл + роль), общий workspace, context. Реализовано:
`/team start <имя> [задание]` спавнит участников **внутри текущей сессии**
через общий шов сабагентов (не отдельные терминалы и не A2A-пиры), хэндл
нормализуется тем же `sanitizeAgentId`, что и id реестра (`agent://<id>`),
поэтому `/team status|stop`, контекст и список пиров используют этот id.
Участники общаются напрямую через IRC `agent://`; team-спавн выдаёт полный
`write` даже read-only агенту. Он не ограничен адресами `agent://` и позволяет
также писать файлы с учётом действующих политик доступа; обычные спавны вне
команды не меняются. Если указан workspace, `/team start` создаёт там
`TASKS.md`, если его нет, и не перезаписывает существующий. Участники заявляют
задачи строкой `owner: <нормализованный-хэндл>`; это соглашение, не атомарная
блокировка. Без workspace файл автоматически не создаётся. `/team stop`
освобождает только записанные при старте ref id (tombstone, транскрипты
сохранены), а не любой ref с таким же хэндлом. Нет файлового mailbox,
split-pane, idle-уведомлений и shutdown request/approve; команда не
кросс-терминальная. Гейт: `team.enabled` (default off); кап:
`team.maxTeammates` (default 4). [docs/agent-teams.md](docs/agent-teams.md)

## Известные ограничения

- `hops` расширяют только wake-relay; ручной ответ агента начинает цепь заново;
- pending-спавн A2A после 30 с grace получает FAILED (поллинг GetTask по taskId);
- `refusalReason` телеметрии v1 — только concurrency_limit;
- выключение chrome через per-server `enabled:false` не работает — используйте
  `disabledServers: ["chrome"]`;
- workflow не прерывает async-цикл после первого await (только sync-часть).

## Отличия от upstream omp (кратко)

| Область | upstream | форк |
|---|---|---|
| Кросс-терминальный обмен агентами | нет | A2A-мост (сервер+клиент) |
| Браузер по умолчанию | изолированный Chrome for Testing | ваш Chrome (browser relay; chrome-mcp автодискавери остаётся) |
| Anti-flood в IrcBus | нет | rate/dedup/hops/backpressure |
| Перегруз спавнами | тихая очередь | опциональный refuse с числами |
| Токен-бюджет | нет (только requests) | `<total_tokens>` в контексте |
| Оркестрация workflow | нет | VM + journal + resume |
| Деструктив | без подтверждения | одноразовые capability-токены |
| Спавн из расширений | нет | pi.spawnSubagent |
